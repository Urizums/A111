# 后续路线与阶段

按可验证结果推进，每阶段建议 3–5 个任务。当前首项由 state/phase-todo.json 指定；长期路线不自动授权付费服务、发布或真实业务审批。

| 阶段 | 可交付结果 | 关闭条件 |
| --- | --- | --- |
| S00 交接 | 可移植源码、历史、提示词、状态和独立接续测试 | 解压/换路径检查通过；实际启动 S01 首项 |
| S01 C1 收尾 | 只读审计、按冻结 C01–C10 判定、同步 partial 与证据 | 缺口逐项记录，不假装性能有效；最后启动 S02 首项 |
| S02 方法修订 | Root 写首条域内采集命令、instrumentation 边界、真实 receipt 状态顺序、修正分母与 worker 工具范围 | 新候选、源码哈希与要求先冻结；最后实际启动 S03 烟测准备 |
| S03 Luna 合规烟测 | 一个全新普通 worker，原验收闭环、真实原生返回、输出范围及失败留证 | 不接触旧结果；无论通过/失败保存实际状态；失败有界修复或 blocked |
| S04 条件式性能实验 | 在 S03 合规后才冻结新配对、顺序、输入、预算与计时定义 | 保留所有样本/辅助/缺失；不足则 inconclusive，不为出数字重跑旧样本 |
| D1 设计预设支线 | 小型版本化 catalog：来源、适用任务/平台、tokens、组件状态、motion、可访问性 | Root 作者，Luna 调研预处理；结构与真实渲染结论分别记录 |
| R1 运行时支线 | provider SDK adapter、遥测/全局限制、自然网络事件、外部业务效果对账 | 四项单独案例、权限与 host 能力现场核实，不被本地 fixtures 代替 |

S01 与 D1 材料准备可并行；共享源码/台账由 Coordinator 整合。R1 各子项不必等无效性能比较“成功”，但需要其自身接口、可执行 host 与冻结案例。没有有效 setup 瓶颈证据时，不优先加初始化助手。

## 阶段转换

完成当前阶段的实质任务后，先写下一阶段 TODO（明确首项、写域、验收和预算），执行首项的真实首步并保存返回，再把本阶段末项“启动下一阶段任务”设为 done。下一阶段首步可以是源码检查、冻结具体实现契约或实际执行，不可以只有“已开始”的文字/空文件。

目标已经满足时记录终态，不制造下一阶段。只剩需新权限/不可用能力的任务时转换项保持 blocked，保存已完成的独立工作。新的发现先形成追加需求与影响，再决定是否属于当前目标；不无限扩大范围。

## 运行中收敛

默认一个候选两轮修复。先完成能影响结果的功能或测试，不连续堆叠计划。每轮记录改变、原因、实际检查、残留问题和下一可执行动作；消耗的额度跨中断保留。不要因当前阶段未完就清空 TODO。
