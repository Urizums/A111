# Experience and interface design

Use this guide when the requested product has a user interface. If the task has no UI, do not invent a screen, mockup, or visual artifact.

## Work from evidence to an original interface

1. **Name the job and context.** Record the user's main task, audience, frequency, content volume, device, input method, accessibility needs, and the cost of mistakes. Identify the current task path and failure or interruption that matters.
2. **Sample real products.** Choose references for the same platform and task. Observe complete paths and states, not just hero screens. Record URL, date, exact observation, and source/use limits using [the reference matrix and sampling steps](design-references.md). Separate what was seen from what you infer. A reference is evidence of an observed design, not proof that it fits this audience.
3. **State a design hypothesis.** Map each useful observation to an explicit assumption about this user's task and a predicted benefit. Keep the hypothesis falsifiable: for example, “placing the last-used filter above the run list should reduce filter changes in the repeat-run task.” Record a measure and a rollback trigger; do not report an expected benefit as an outcome.
4. **Define semantic tokens.** Name tokens by role and pair foreground/background roles. Keep palette choice independent from layout and density. The supplied [CSS presets](../assets/ui-presets.css) and [local demo](../assets/ui-presets.html) are original starting points, not a third-party brand reproduction. Reuse third-party CSS, components, assets, or design-system material only when the current terms allow it; pin the source revision and keep required notices. If permission is unclear or reuse is not allowed, translate observations into original tokens and components.
5. **Shape the page around the task.** Give the primary repeated action the clearest placement and one visual priority. Choose a table, list, form, canvas, timeline, or text-first layout when it fits the content; use grouped surfaces only to show real relationships. Set hierarchy with the combined effect of region size, position, spacing, density, typography, rules, and color. Do not turn every item into an equal card or use accent color as decoration. Check representative long labels, empty results, and realistic content volume before locking proportions.
6. **Specify behavior alongside the visual hierarchy.** Make frequent actions discoverable in the place the task needs them. Define navigation and current location; what Close, Back, and Exit do; what happens to a draft; how filters and mode switches take effect; and which state persists. Keep destructive actions contextual and visually restrained; ask for confirmation when the consequence warrants it. For a dialog or drawer, provide a named close control, support the platform's back/escape behavior, and preserve the underlying task.
7. **Design states before polishing.** Define input routing when keyboard, scanner, touch, shortcuts, or repeated activation can reach the same view; name the active state, destination and busy-state queue or rejection behavior.  Loading must leave existing useful content available, expose a meaningful status, and allow cancellation. Provide retry after a recoverable failure. Bind each response to its request/version and ignore or abort stale work before it can overwrite newer state. Never use a fabricated percentage for work with no measurable denominator. Disabled, invalid, error, empty, success, and selected states must remain understandable without color alone.
8. **Use motion to explain change.** Follow [motion design](motion-design.md) for entrance, exit, expansion, side or diagonal slide, spring candidates, interruption and focus. For each motion, state its purpose and the state transition it clarifies. Honor reduced-motion preferences with a usable static alternative. Avoid adding delay to make a response feel smooth; measure real wait time and show feedback promptly. Treat responsive breakpoints, debounce periods, and timing thresholds as hypotheses: record how they were chosen, measure task/device data, then tune them. They are not general service-level guarantees.
9. **Implement and inspect the actual journey.** Build the smallest complete path in the real target stack. Record the command/build identity, actual browser or device, viewport, starting state, and a reproducible route such as “Runs → filter Failed → open latest run → close details → retry.” Inspect that path in the running product at relevant widths, with keyboard and pointer/touch input. A static HTML preset is a component/layout reference, not evidence that another app works.

## Keep visual and behavior evidence distinct, but linked

Give the target hypothesis and journey one shared identifier. For visual review, record the viewport/device, theme, density, screenshot or recording, and an independent reviewer’s observations about hierarchy, spacing, contrast, clipping, and state presentation. For behavior review, record start state, actions, focus/back behavior, visible feedback, persisted state, and actual request or result. Link both records to the same hypothesis and journey. A screenshot establishes only what was rendered at that moment; it does not establish task completion, behavior, or permission to reuse an asset.

Preserve the exact source revision or snapshot, commands and raw results before repairing a reviewed candidate. Keep original findings separate from checks that expect the corrected behavior. An assertion that reproduces a bug proves the bug was observed, not that the product passed. If the original source was not retained, name that reproducibility limit.

For asynchronous journeys, bind a result to its originating route/document or record, request identity and relevant revision. Separate the operation’s actual outcome from the current view: closing a layer or changing context must not lose a confirmed save, attribute it to another record, or let a late result overwrite a newer draft. Include an out-of-order response or acknowledgement-loss case when that risk is material.

Use WCAG 2.2's Understanding pages as checks, not as a substitute for testing: normal text needs at least 4.5:1 contrast, while large text uses 3:1 under the criterion's definition; meaning must not rely on color alone. The guidance on animation from interactions is Level AAA; do not label every motion restriction as an AA requirement. On mobile, include system bars, insets, and platform back/navigation behavior in the actual device review. See [design references](design-references.md) for source scope and limits.
