# Motion design

Choose motion to clarify a user task, state change, or spatial relationship. Select effects for the target platform, content, input, and consequence of the action. Do not make every component bounce or fade merely to make an interface feel lively. A control can respond immediately without an entrance effect, and a usable interface should not make a user wait for a flourish before continuing.

Treat distinct motions as distinct decisions. **Entry and exit** can reveal where new content came from or where dismissed content went; keep essential actions available promptly and avoid delaying an entire screen behind a decorative sequence. **Expansion and collapse** can clarify that a region grows within its current context; keep labels, controls, and reading order understandable as its size changes. **Side slides** can communicate a drawer, inspector, or temporary layer when that spatial relationship matches the platform and task. **Diagonal shifts** need a specific meaning, such as moving between connected workspace regions; otherwise they can obscure direction. **Elastic or spring-like motion** may suit direct manipulation or a lightweight object settling into position when target-platform conventions support it, but can feel playful or unstable for serious, dense, or high-stakes work. Use staggered layers or backgrounds only when they help establish hierarchy; they are candidates, not required waiting steps. Separate these component transitions from ordinary document or viewport scrolling. Prefer the platform’s normal scroll behavior unless there is a verified task-specific reason to change it.

For each meaningful motion, record a traceable specification with:

- **Trigger and semantic state:** the user or system event, the state before and after, and the relationship to the actual application state.
- **From, to, and direction:** the visible property and spatial direction, including whether content enters, leaves, expands, contracts, or settles.
- **Timing source:** duration and easing or spring source. Cite a relevant current platform or component-system convention, observed product reference, or measured target-app result. If none is established, label timing and curve as a tunable local hypothesis; do not invent global duration limits, spring constants, or platform rules.
- **Delay and purpose:** say whether any delay serves sequencing or comprehension. Do not add waiting for polish, or let a stagger imply that later content is unavailable.
- **Interruption and reversal:** define behavior for repeated activation, navigation away, dismissal, request changes, and reversing direction. Cancellation must leave the semantic state coherent; an old completion or cancellation event must not overwrite a newer state. Animation completion is not evidence that a business operation succeeded.
- **Focus and input:** state how keyboard focus and pointer/touch interaction behave while the effect runs. Move focus according to the semantic interaction and available controls, not to match a visually flying element. Preserve expected keyboard order and return behavior when a temporary layer closes.
- **Layer contract:** identify modal or modeless behavior at each relevant viewport, background interaction and scroll, concurrent-layer exclusivity or stacking, and backdrop dismissal. Define focus entry and return for each opening trigger; if the original control disappeared, name a stable fallback in the originating context.
- **Performance conditions:** note the target device, content volume, and any relevant profiling evidence. Stable identity and transform/opacity use may be reasonable implementation candidates, but do not claim that an animation avoids layout work, is smooth, or is inexpensive without measuring the actual target. Avoid forced read/write layout loops; verify the suspected bottleneck before making application-wide changes.
- **Reduced-motion alternative:** define a useful static or greatly simplified presentation that reaches the same understandable state without relying on movement.
- **Acceptance evidence:** define how to verify the state change, input, and visual result in the actual app.

Keep business state independent from animation callbacks. Update the state from the action or operation result, then let motion present the transition. For asynchronous work, associate results with the current request or version and discard stale responses; canceled or late animation events must not restore an older visual state. If an interaction is interrupted, permit a coherent immediate end state or reversal rather than leaving content stranded between states. Do not require a transition to finish before focus can reach an available control.

Verify the target app when implementation is requested. Check the DOM or accessibility tree for the expected semantic state and focus location, and separately inspect that the intended transition actually runs. Exercise rapid repeated open/close or expand/collapse, cancellation, reversal, reduced-motion settings, long content, and lower-performance conditions when relevant to the feature. Confirm content remains operable and does not clip, jump, or block scroll. Choose checks proportional to risk and platform. If only methods, source, or fixtures can be inspected, label that evidence accurately and leave browser/device acceptance unclaimed; do not bypass unavailable browser access. When motion changes frontend state handling, performance assumptions, or accessibility behavior, send those scoped implications through Forge’s traceable integration and acceptance process instead of refactoring unrelated application areas.
