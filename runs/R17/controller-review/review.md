# R17 controller review

**Verdict:** `runs/R17/acceptance.json` delivery.d1 is **not met**. The new path usefully removes the business-wide two-retry stop, binds retry notes to retained evidence, and rejects an identical retry rationale. However, executable probes found two material evidence/guard gaps: a configured deadline can be exceeded and still produce `done`, and completed work can have its frozen acceptance weakened while `validate()` reports no errors. A retry can also reuse the exact same finished command receipt; this undermines the claim that the changed action was actually performed.

## Scope and evidence

Read only the assigned `AGENTS.md`, `scripts/continuation.py`, `scripts/test_continuation.py`, `scripts/record_command.py`, `runs/R17/scope-decision.json`, and `runs/R17/acceptance.json` (including delivery.d1). Did not inspect author reports, ledgers, previous regression output, other agent results, or shared state. Temporary probes, their fixture, and command receipts are under this directory. The behavioral probe ran in Ubuntu-24.04/WSL with Python 3 `-B`; it used a tiny local `delivery.read_file` shim because `delivery.py` was outside the read scope.

`legacy-tests-command.json` records the supplied continuation tests: 12 tests passed. `probe-command.json` records a real successful child command and the deadline-crossing probe. `immutability-probe-command.json` records the same probe after adding a post-completion acceptance mutation. An earlier shell-quoting attempt failed before a command receipt could be made; that invocation did not reach the test process and is not evidence of a product failure.

## Required defects

1. **Deadline is not an actual completion boundary.** `stop_reason()` checks the deadline at selection/start time (`scripts/continuation.py:60-79`), but `finish()` only converts a failed result to blocked when a stop reason exists; a passing result is unconditionally `done` (`scripts/continuation.py:231-263`). The probe began under a future deadline, changed it to an expired deadline, then finished with all criteria passing: output was `deadline_success: done`. This means a task can overrun its declared resource window and be credited complete. Recheck the boundary before accepting success (and document that command execution itself remains cooperative unless it is separately bounded).

2. **Frozen acceptance is not checked after completion.** `finish()` checks the acceptance hash while an attempt is active (`scripts/continuation.py:237-245`), but `validate()` does not compare a terminal task's current acceptance against its recorded attempt hash (`scripts/continuation.py:111-184`). The second probe changed the assertion after `finish()` had marked the task done; `validate()` returned `[]`. This allows a completed result to survive weakened or rewritten acceptance. Terminal acceptance should remain bound to the hash recorded for the completed attempt, with drift reported as an error.

3. **Retries do not require a new actual execution receipt.** `begin()` verifies only that the referenced JSON says `finished` and contains argv, integer exit code, begin, and end (`scripts/continuation.py:196-229`). It does not require a new receipt per attempt, reject reuse of an earlier start-evidence hash, or bind the changed recovery action to a newly executed command. The supplied `test_progress_recovery_beyond_two_retains_all_failures` uses the same `step.json` receipt on all four attempts (`scripts/test_continuation.py:96-110`); that path passes. Consequently, distinct narrative/evidence notes can advance the retry counter while the actual recorded action stays identical. Require fresh receipt evidence for retries and retain it per attempt; semantic progress still needs the human/host judgment described in the policy.

## Requirement findings

- **Old fixed behavior — pass for the exercised behavior.** Non-progress tasks retain numeric `repair_limit` validation and eligibility checks (`scripts/continuation.py:60-65, 99-105, 142-159, 207-216`). The legacy test confirms initial attempt plus two repairs, then no further ready attempt; all 12 supplied tests passed. The fixture does not establish byte-level immutability of historical R17 records.
- **New progress behavior — partial.** No global two-repair cap is applied to `progress_guard`; the test makes four attempts (three retries) and succeeds. A retry requires observation, changed action/new information, expected check, evidence with matching hashes, and a recovery signature not already present (`scripts/continuation.py:81-97, 207-229`). Exact replay of the same note is rejected in the test. The receipt-reuse defect above means the changed action is not evidenced as executed. A `stalled` state and an expired deadline block ready work; the deadline success overrun remains a required defect.
- **Authority and resource boundary — partial/limited.** `record_command.py:27-44` keeps a started/finished child-process record, captures stdout/stderr, and returns its exit status, but `subprocess.run()` has no timeout. The controller is cooperative: metadata and `stop_conditions` are not a provider quota, process sandbox, or semantic-progress oracle. The progress guard only mechanically interprets `progress_state == stalled` and `deadline_utc`; arbitrary `stop_conditions` text is not executable policy (`scripts/continuation.py:66-79, 140-156`). Record explicit refusal/resource-stop observations and use the block path; current code cannot infer their meaning from arbitrary output. This limitation should remain explicit in claims.
- **Evidence and history — unknown for the real R17 state.** The source validates hashes of referenced inputs/results and locks acceptance during an active attempt, but this review was prohibited from reading continuation state or historical evidence. No claim is made that historical bytes, counters, or prior verdicts did or did not change. The fixture only establishes the post-completion acceptance-drift defect in current code.
- **Independent review / research trial — not assessed here.** This assignment supplied controller sources and delivery.d1 only; the search trajectory, source-selection evidence, and independent policy judgments remain unknown.

## Optional improvements

- Reject or normalize `write_paths` containing `..` and absolute paths before overlap checks. The guard compares lexical `Path` values (`scripts/continuation.py:188-194`), so traversal-shaped names can evade the intended overlap comparison. This is a cooperative concurrency guard, not a filesystem permission boundary.
- Validate `stop_conditions` against a structured set of human-actionable conditions, or label the field clearly as documentation. It currently accepts any non-empty list and does not affect scheduling.
- Keep `record_command.py` telemetry limits prominent: it captures full process output in memory and has no cancellation/timeout mechanism. These are host limitations, not evidence that an actual provider limit was observed.

## Source-backed verdict for delivery.d1

The existing tests and probes show meaningful legacy/new guards, but the post-completion acceptance drift and deadline-overrun paths fail the acceptance. The required fixes above need fresh behavior checks. Actual historical byte checks and immutable-history conclusions are **unknown** under this review's read boundary.
