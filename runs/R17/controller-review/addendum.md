# Controller review addendum

This addendum preserves the original review and its historical `delivery.d1_not_met` verdict in `review.md` and `review.json`. It assesses the later source version independently; it does not rewrite the earlier observation or any historical R17 verdict.

## Updated-source findings

I reread the current allowed sources after the implementation changed. The current full test command is recorded in `addendum-tests-command.json`: all 15 tests passed. The controlled behavior run is recorded in `addendum-probe-command.json`; a repeated run using a fresh fixture (which also includes the legacy acceptance-drift check) is recorded in `addendum-legacy-freeze-retry-command.json`.

- **Deadline completion boundary: repaired for a progress-guard task.** I created a deadline 0.6 seconds ahead using the real UTC clock, began before it, waited 0.9 seconds, and finished with passing criteria. `finish()` returned `blocked`, retained the result ref, and recorded the declared deadline as blocker. This is a real local elapsed-time check, not a provider quota or background-process timeout. The supplied mocked-clock test also passes.
- **Terminal acceptance freeze: repaired for progress-guard tasks; still open for legacy tasks.** After a successful progress-guard completion, changing the acceptance assertion makes `validate()` report `changed frozen acceptance`. But an equivalent completed task with no `execution_policy` can have its assertion changed and `validate()` returns no errors (`legacy_acceptance_drift_errors: []`). Current validation checks the latest requirements hash only inside `if progress_policy(t)`. The controller already stores a requirements hash for legacy attempts, so historical fixed-policy completions are still mutable without detection. This is a required remaining defect against immutable history/acceptance.
- **Fresh retry receipt: repaired for exact receipt reuse in progress mode.** After a first failed progress attempt, reusing the same receipt hash was rejected with `Progress retry requires a fresh actual execution receipt`; a newly recorded second command was accepted. The legacy fixed-policy path still permits receipt reuse, as observed, while retaining its configured repair cap. Receipts remain cooperative local telemetry: distinct JSON receipts do not prove semantic progress or provider execution.
- **Legacy opt-in behavior: pass for the exercised retry cap.** A task without `execution_policy`, configured with `repair_limit=1`, completed two failed attempts (initial plus one repair), then became blocked with `repairs_used=1` and no ready task. New progress behavior remains opt-in through `mode: progress_guard`; this probe did not inspect actual historical task state or prove byte preservation there.
- **Policy source/config freezing: pass for tested fields.** The supplied test mutates the bytes at the policy source path and validates drift; the current suite passes. It also changes deadline policy after completion and observes `changed frozen execution policy`. The current `policy_identity()` excludes only `progress_state`, so the runtime transition `ready` to `stalled` remains valid while mode/source/deadline/stop-condition terms stay frozen. In my probe, setting `stalled` during an active attempt left `validate()` clean and a successful finish became `blocked` with the stalled-path reason.
- **Malformed deadline policy: required remaining defect.** `deadline_utc: ""` passes validation and leaves a planned task ready, silently acting like no deadline (`empty_deadline.errors: []`, `ready: ["t"]`). The intended no-deadline value is `null`; non-null values should be a timezone-aware string. A numeric value (`123`) raises uncaught `AttributeError: 'int' object has no attribute 'replace'` during validation instead of producing a schema error. This is both silent boundary removal for falsey malformed values and an uncontrolled failure for truthy wrong types.

## Current verdict

The updated code repairs the three previously observed progress-path defects: deadline-overrun completion, progress completion acceptance drift, and exact retry-receipt reuse. The d1 result remains **not met** because terminal acceptance drift is still undetected for fixed/legacy tasks and malformed falsey deadlines can silently disable the only declared local resource window. The earlier verdict remains preserved as historical evidence. Historical bytes, counters, and old task records remain **unknown** because they were outside this review's read scope.

## Limits and failure retention

The probes use `record_command.py` for outer command receipts and for actual child commands. `addendum-legacy-freeze-command.json` preserves a failed rerun: its fixture reused a prior exclusive receipt path and `record_command.py` refused the duplicate before the test body ran. I then reran with a new fixture path and unique output receipt; that result is `addendum-legacy-freeze-retry-command.json`. This failed setup attempt is not a product-code failure.

The 15-minute window is local wall-clock/command telemetry. The controller is cooperative and does not impose provider quotas, hard process isolation, or semantic progress. Distinct receipts and recovery notes are not proof that a changed action improved the result.
