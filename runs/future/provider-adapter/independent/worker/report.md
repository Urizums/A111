# Independent provider-adapter acceptance report

**Outcome: local protocol acceptance passed.** The frozen acceptance checks all passed on both Python 3.12.14 and Python 3.10.21. Each runtime run exercised 55 actual CLI subprocesses and 62 assertions, with the complete commands, stdout/stderr, exit codes, and post-process SQLite state saved in `results.json` and the per-runtime logs.

The tested files were the frozen [`contract.json`](/workspace/A111/runs/future/provider-adapter/contract.json) and [`adapter.py`](/workspace/A111/runs/future/provider-adapter/adapter.py). Their SHA-256 values were respectively `625797bfcda0365b1669dc2d02e5ee4e17e902427c7a3449d22e3a437ff8036a` and `b6fb2ae7b74079017d105f072892cddab5c0c6341c5348331c6c34d8a86171cd`.

The CLI committed `req-main` before returning `should_dispatch: true`. A semantically identical retry, including a JSON object with reordered keys, returned the same request with `should_dispatch: false`. Changed payload under the same idempotency key and changed content under the same request ID were refused without changing the stored request. After an ambiguous outcome was observed as `unknown`, reopening the SQLite database showed that state and event history; retry still returned `should_dispatch: false`. A matching `run-A` observation advanced the record through `running` to `succeeded`.

Cancellation tests covered both outcomes. For `req-cancel-success`, cancel returned `cancel_requested: true` and `terminal_proven: false` while the request remained running. A later success observation settled it as succeeded while retaining the cancellation intent. For `req-cancel-ack`, cancellation intent alone remained nonterminal; an explicit `cancelled` observation made it terminal. Fresh CLI processes reopened and read both histories.

Event checks confirmed same-event replay is idempotent, changed content under an existing event ID is refused, provider-run identity drift is refused, and a new contradictory terminal observation is refused. Unknown request identity and invalid event shapes were rejected. The suite rejected malformed JSON, duplicate JSON keys, `NaN`, unknown request/event/usage fields, booleans and invalid values for limits or usage, invalid identities, and an invalid event status. Unavailable usage remained JSON `null`; no usage was turned into zero. A simultaneous pair of local submissions for one identical request produced exactly one dispatch decision and one durable request.

The exact request limits accepted by this adapter are `timeout_ms` and `max_output_tokens`; each must be a JSON integer of exact Python type `int` and at least 1. Booleans are rejected. The adapter declares no upper ceiling for either value. The input must be nonblank text. Request, model, event, and non-null provider-run identifiers must match `[A-Za-z0-9_.:/-]{1,128}`. These are local input-validation rules; they do not impose global or provider-side limits. The implementation performs no provider SDK execution and the evidence makes no live execution or authenticated telemetry claim.

Committed request IDs and final durable statuses were `req-main` → `succeeded`, `req-cancel-success` → `succeeded` with cancellation intent retained, `req-cancel-ack` → `cancelled`, `req-event-invalid` → `unknown`, `req-limits-min` → `accepted`, and `req-concurrent` → `accepted` with one dispatch decision. Invalid requests created no rows.

Tokens, cost, provider identity, and model-active-time were unavailable and are `null`. No network or external provider was used. The harness failures, their output and corrections, plus a rejected workspace-reset command are preserved in [`attempts.md`](/workspace/A111/runs/future/provider-adapter/independent/worker/attempts.md); the original partial-run directories and successful per-runtime logs remain in the worker directory. No parent questions were asked.
