## Preprocessed candidates

Every layout, breakpoint, state name and token below is an **inferred original candidate**, not an observed screen. The cited standards and platform pages support the accessibility and inset hypotheses; they do not establish that a particular arrangement improves task performance.

### Dense review console — desktop web, with narrow web fallback

- **Region / attention map:** queue context and global actions at top; filter/search band next; a scannable queue as the primary region; selected record and decision/activity detail beside it at wide widths. Keep decision actions with the selected record. At a narrow width, replace the side-by-side arrangement with a list-to-record route so columns do not force hidden horizontal content. The split view is a task-based hypothesis; no reviewed flow supports it.
- **Candidate pairs:** canvas `#F3F6FA` / body `#17212B`; white card `#FFFFFF` / `#1F2937`; secondary `#475569` / canvas; selected `#DBEAFE` / `#1E3A8A`; action `#1D4ED8` / white; warning `#FFFBEB` / `#854D0E`; error `#FEF2F2` / `#991B1B`. Selection, status and error each also get a text label or icon, as applicable, so hue is not their only cue (Use of Color).
- **Component states:** queue loading has a text status and static placeholder rows; loaded rows expose owner, state and updated-time text; empty queue distinguishes “no work assigned” from “no results—clear filters”; fetch error keeps filters and offers Retry; submit conflict shows both the server and local versions, with explicit compare/keep/replace actions. Preserve entered work after validation or network errors as a product hypothesis.
- **Keyboard/focus:** visible persistent ring on filters, row controls, detail links and decisions; proposed tab sequence follows filter → queue → current record → decision controls. A conflict/irreversible-change confirmation can use native `dialog.showModal()`, deliberate initial focus, explicit Cancel/confirm buttons and Esc dismissal, then be checked for focus restoration. Do not rely on a mouse-only selected-row treatment.
- **Motion:** no motion is needed for the state change; if row/detail transitions are added, the reduced-motion branch removes or replaces sliding/panning with a static state update. Keep status text and focus position stable. MDN documents the preference, not this exact interaction.
- **Verify:** keyboard-only pass across an empty, populated and conflicting queue; check each actual text pair and all status labels; test wide (e.g. 1280 CSS px), intermediate and 320 CSS px viewports for clipping/return paths; enable OS reduced motion and ensure no information depends on movement; test conflict Esc and focus return in supported browsers. These widths and outcomes are test hypotheses, not source-derived breakpoints.
- **Alternative and choice:** a single full-page record route is simpler and safer for narrow views, while a wide split view may reduce context switching for review. Keep split only above an empirically chosen breakpoint; narrow fallback avoids shrinking the queue and detail into unreadable columns.

### Handheld stock-count form — phone web, Android host caveat

- **Region / attention map:** compact job/location context → item identity and unit → one primary quantity field → optional note/exception → save/next action and a textual sync state. Keep one item’s count in view while the keyboard is open; let the document scroll instead of anchoring an action beneath the on-screen keyboard. If hosted in an edge-to-edge Android app/WebView, apply system insets and keep action targets clear of status/navigation/gesture zones.
- **Candidate pairs:** canvas `#F8FAFC` / body `#1F2937`; white input/surface `#FFFFFF` / `#1F2937`; action `#1D4ED8` / white; saved `#ECFDF5` / `#065F46`; conflict `#FFFBEB` / `#854D0E`; invalid `#FEF2F2` / `#991B1B`. Text, icon and label accompany color. Use a persistent focus treatment that remains distinct on canvas and white input.
- **Component states:** item fetch loading uses a static label/placeholder; no assigned item offers a clear next route; quantity validation shows a field-associated text error and preserves the entered value; save-in-progress disables duplicate submit while retaining a visible busy label; offline save reports “saved on this device / waiting to sync” only if the product actually persists locally; a server/local count conflict presents both values and explicit resolution; completed count gives text plus check. Local persistence and offline semantics are requirements to verify with the eventual product, not inferred from Android guidance.
- **Keyboard/focus:** labels remain visible above their controls; proposed tab order is item context → count → note/exception → Save/Next. Show a visible ring and don’t move focus to an error solely by color. If a modal conflict is chosen, use the native dialog pattern and keep a clear cancel route; test on physical Android plus desktop keyboard emulation.
- **Motion:** submit/error/sync state updates do not require motion. Honor `prefers-reduced-motion` by suppressing any spinner sweep or animated count transition while preserving a textual progress/saved state; do not use large panning/scaling effects.
- **Verify:** Android edge-to-edge and gesture navigation with the IME open; system bars/cutout/folded and compact widths if those are supported; zoom/text scaling; rapid repeated save; bad count; offline/reconnect; stale server count; no item. The source establishes inset concerns, not web touch sizes, input behavior, or a responsive breakpoint.
- **Alternative and choice:** a fixed bottom Save button may be easy to reach, but can be obscured by IME or gesture/system insets. Start with an in-flow action and test reachability; use a fixed action only if device testing proves it remains visible and unobscured.

### Long-document reader and annotation — responsive web

- **Region / attention map:** document title and compact controls; optional/collapsible contents navigation; one continuous reading column; annotation affordance kept near the passage it affects. On narrow screens, collapse contents navigation and keep the document as the dominant region. Page width, font size and sticky behavior are unmeasured original layout hypotheses.
- **Candidate pairs:** reading canvas `#FBFAF7` / body `#2F2D2A`; secondary `#475569` / reader canvas; white utility surface `#FFFFFF` / `#1F2937`; annotation `#FFF1C2` / `#3A311E`; action `#1D4ED8` / white. Annotation also receives an icon/underline/explicit “comment” label, never highlight color alone.
- **Component states:** document load has a static placeholder and text status; no content explains the empty state and offers Back; fetch error offers Retry without losing the return path; selection/comment composer distinguishes draft from saved note; a simultaneous edit shows the conflicting local/server text and explicit resolve, keep, or discard choices; deletion/unsaved-exit may use a clearly labeled native confirmation dialog. Conflict details and return behavior are product hypotheses.
- **Keyboard/focus:** visible focus for contents links, search, highlights, note actions, dialog controls; tab order follows document controls before annotation actions where possible; opening a conflict dialog sets a deliberate initial focus, offers an explicit close/cancel and supports Esc. Do not create keyboard traps in annotation controls; verify reading/navigation semantics with screen readers because these sources do not specify the document’s accessibility structure.
- **Motion:** no auto-panning or parallax is required. With reduced motion enabled, navigation to a heading/annotation reaches the same semantic destination without smooth animated travel; retain the user’s place and visible focus. Test browser behavior and focus/scroll interplay.
- **Verify:** long and short documents; narrow viewport and browser zoom; keyboard-only navigation among contents and annotations; reading order with screen reader; active, empty, failed and conflicting comments; every text pair; reduced motion. No evidence here establishes a preferred typography scale, page width, scroll model or annotation workflow.
- **Alternative and choice:** sticky contents can aid orientation in wide documents but consume vertical/horizontal space and can obscure content when zoomed. Start with collapsible contents and no sticky panel; adopt stickiness only after viewport/zoom and long-document testing.

## Fit, reuse and open questions

The chosen alternative is an original semantic palette plus task-shaped layouts and state coverage, because the public visual lead exposed categories but no specific opened item, while the primary documents support accessibility behavior rather than visual identity. No assets, screenshots, code, or third-party preset values were reused. Refero’s exact material reuse terms, and all page-specific asset terms, were not checked; reuse is therefore not proposed.

Open questions for target evaluation: exact queue fields and whether reviewers compare records side-by-side; whether stock counts must work offline, support barcode scanners, gloves or outdoor glare; whether the reader needs simultaneous annotations, collaboration or mobile pagination; supported host/browser/platform matrix; product type scale/brand palette; persistence and conflict semantics. These gaps affect actual hierarchy, safe offline states and responsive choices. All three candidates need rendered checks and task testing before adoption.
