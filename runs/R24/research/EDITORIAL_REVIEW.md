# C14-lean 编辑与维护性审阅

**审阅性质：作者静态走查。** 已经修改了真实候选文档并执行链接、metadata、Git 身份等静态核对；没有新的独立 Agent 运行、模型比较、浏览器测试或正式候选晋级。原 C13 与 C14-hypothesis 均未覆盖。

## 为什么修改

先前文档的表达非常严密，但部分结构会反过来限制使用者：固定的“Step/Owner/Check/Failure”表容易被理解为一切工作都要建流程表；研究 R25–R28 的逐节点编号看起来像已经确定的强制开发流水线；长篇交接清单让小任务也倾向于产生过量元文档。

C14-lean 把主要判断改写成自然语言：从结果开始，依据依赖选择协作，用真正相关的证据判断是否正确，再根据观察修复。仍使用九文件结构是为了保持主题路由与可移植 Skill 包接口稳定，而非认为九份是永远正确的数量。

## 简化而不丢失原有重要能力

- **交付义务。** 一个短 JSON/文档抽取不需要工作流工厂；如果明确要求 A、B 两个方法分别给结果，不能用只推荐 A 代替 B。Skill 和 workflow-design 均明确处理。
- **运行证据。** 设计、命令成功、真实运行、独立接收与广义可靠性依然不同；无法运行的浏览器不能靠截图或静态检查过门。见入口与 evaluation/frontend 参考。
- **信息污染。** 独立验收必须检查实际能看到的历史、argv 和摘要；写域分离不自动等于盲审。见 collaboration。
- **失败和连续性。** 保留原样本/旧失败/资源、不要盲重复、不虚构后台行动，也不把两次工具错误当作全任务停止条件。见入口、continuation、iteration-and-recovery。
- **领域职责。** 建模中的决策时点、数值/目标重算，研究的来源适用性，UI 的真实交互检查继续留在按需参考，而非压缩进入口。
- **维护边界。** 新经验先保留成研究案例；具有跨任务必要性和实际观察后才提升 Skill 原则。改候选不修改 release 根文档或历史锁。

## 后续改进应如何实施

首先测试阅读者是否将条件性建议误读成强制步骤，例如是否给单次任务造出多 Agent 组织；其次才比较必要交付遗漏。真正的新候选试验需要把输入和检查标准先冻结，不能用本次已公开的静态反例冒充盲测。发现重要职责消失时，优先修复对应句子及受影响检验，而不是回退到全篇僵硬模板。若没有实测提升，可保留精简稿作为编辑探索而不推广。
