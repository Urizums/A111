# Forge 的方法层应该留下什么

Forge 的核心不是一套固定的角色或流程图，而是帮助执行者在不同任务里做正确的选择。最值得长期保留的知识应告诉读者：在什么情形下做什么决定，为什么这样选择，以及如何发现选择错了。

例如，一个短文档抽取任务可以直接做完并核原文；一个需要两种预测结果、还要提交最终建议的任务则需要明确区分“都必须交付的结果”和“最后推荐的方案”。再复杂一点，当不同 Agent 接力时，消费者需要知道源数据、单位、版本、可接受状态和失败路线；如果一直是同一人在做很短的事，写出一套完整 JSON Schema 反而没有收益。

## 方法、执行与研究需要相互支持，却不应该混在一起

Portable Skill 负责可迁移的判断方法。宿主执行器处理真实调用、文件、状态、资源与故障恢复；运行代码必须复用或适配当前环境的能力。研究库保留试验条件、负例与版本历史。这三个层次可能互相引用，但不要让 Skill 隐性依赖研究目录、某个控制器或当前 GitHub 仓库。

设计工作流时，先看用户最终会收到什么，随后是必要的数据与决策、重要的交接接口、真正可以验收的行为，以及可能导致结果无效的边界。表达方式可以是几段自然语言、简单表、图或 JSON。选择由任务规模和消费者决定。

当结果需要独立接收时，独立性是实际信息流属性，不是给某个人标上“Reviewer”。当结果出现错误时，要检查是原需求覆盖不足、数据可用时间错误、目标被偷换，还是工具或验证器出了问题，再决定怎样修复。对没有新信息的重复运行，不应鼓励；有明确新实验时也不应被旧的通用次数规则阻断。

## 怎样才能形成可维护的 Skill

让入口只包含跨任务可用的关键判断和引向参考资料的路由。主题参考资料解决领域特有的问题，案例留在研发目录。一个新案例先提供可验证的观察与反例，确认它对应哪个现存规则的缺口；只有当它改变了普遍的设计决策，才考虑写回 Skill。不要为了体现“学习了更多”就增加字数、强制字段或新角色。

真正应该坚持的不是某种写法，而是结果与原始目标一致、证据不被美化、权限不被扩大、旧失败不被抹掉、已完成与未验证能被区分。

已知的具体观察见 [历史经验](HISTORY_AND_EVIDENCE.md)，候选评估原则见 [验证参考](EVALUATION_AND_CHALLENGES.md)。它们是遇到相关问题时的支持材料，不是 Skill 的隐形必经章节。
