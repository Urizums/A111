# 下一步从什么问题开始

本路线描述**可能的研究顺序**，不是已经开始的多个项目，也不要求每个阶段照表展开。每次推进都应该回答一个真实问题：现有方法有什么可观察的缺口？下一项工作能否改变我们的判断？

## 眼前任务：R24 的文字与行为验证

C13 已保留为方法基线。最初 C14 尝试加强必要性判断，减少需求遗漏；但也增加了抽象术语和重复检查。现在另有 `runs/R24/candidate/C14-lean/`，把流程设计与协作规则改写成更自然、按任务选择的方法。

首先核对候选版本、Git 差异和实际 CI；接着以简单任务、必须分别交付的多结果任务、可能污染独立验收的交接情形，检查文字是否能被正确理解，尤其留意有没有引入无必要的角色、表格或失败门槛。这一步只支持**静态可用性判断**。

真正比较方法效果时，要提供新上下文、未见输入和相同的原任务验收。比较 C13、C14-hypothesis 与 C14-lean 时不必为了凑数量同时跑三个版本；选择足以回答当前假设的基线和候选。记录交付正确性、遗漏、额外负担、误拒收和真实执行限制。旧 R23 的答案已公开，不能把它作为新的盲测证明。没有实际比较，就不要把 C14-lean 称为正式优胜版本。

验证后可以采用全文、只吸收少数有益句子、继续修订，或保留 C13。结论由结果而不是版本号决定。

## 后续研发方向，而非固定装配线

**自主构造（暂称 R25）。** 让 Forge 从陌生需求自然推导结果、关键接口和执行顺序，决定单 Agent 是否足够、是否值得引入独立验证或多方协作。优先试真实但可控的垂直切片，不急着写通用流程编译器。设计是否可执行，与实际任务是否完成，分开评价。

**真实执行和恢复（暂称 R26）。** 先复用仓库现有 CLI、host 桥接、状态和测试设施，再按实际缺口补适配。需要检查幂等、部分完成、未知创建结果和信息泄漏，但不因这些关键词就重建另一套控制器。宿主不支持的动作如实留空，不能用代码模拟替代。

**经验研究（暂称 R27）。** 选择来自真实失败的一个可证伪假设，改变一个有意义的决策或接口，查看是否影响结果。记录负结果与成本；新规律先沉淀为证据卡，跨任务有效才考虑收入 Skill。研究循环可以结束，不能为了“自迭代”制造新阶段。

**可视化与体验（可选，暂称 R28）。** 若真正的 Flow 执行已有可观测状态，而且 TUI/GUI 会帮助人做决定，再考虑界面。没有实际用户流程与允许的浏览器/终端测试，就暂缓 UI 开发。

这些研究可以因风险、工具或结果而调整顺序；真正的项目队列更新应在确认宿主权限、依赖和用户目标之后进行。历史 R08/R23 状态不会因为此路线被提交而被改判。

## 每次工作怎样结束

保留足以使下一个人行动的交付、证据与局限，说明下一步最值得解决的问题。若确实开始了后继任务，记录实际调用；若尚未开始，写“建议”，不标完成。重要副作用、外部发布和实际资源消耗受用户及宿主授权约束。
