# R24–R28 分阶段实施计划与准入门

## 总体机制

以下是**提议中的研发序列**，不是 main 活动任务队列、不是已经启动的 R25/R26/R27/R28。main 的真实阶段仍需查 state/checkpoint.json 和 state/phase-todo.json；历史 R08 阻塞保持。用户已授权整理和规划研究，不能由此虚构工具能力、后台任务或以后自动发布。

每阶段的共同管理约定：开始时核对用户目标/宿主能力/原输入/版本；冻结针对该阶段的验收；先运行一条最小真实路径；看结果、修正有证据的缺陷；由实际消费者接收；写明下一阶段是否有必要及其真实首步。不存在合适后继时记录 cancelled/blocked 而不是完成标记。对于短工作，可以合并步骤，不必单独生成每张表。

## R24：确认 C14 的必要性与实际收益（P0）

**依赖**：C13 原九文件、R23 失败、R24 候选、已有八个提议中的 N0–N7 方向；不得改写 C13。
**现状**：C14 文本候选已在草稿 PR；C13/C14 前瞻比较未发生；CI 必须按最新提交独立确认。
**完成定义**：给出有实测依据的 adopt/revise/reject/partial-absorb 判定，或诚实说明尚缺可用宿主/独立性。

| 工作 | 必要输入与实际动作 | 可检查产物及消费者 | 失败/下一路由 |
| --- | --- | --- | --- |
| R24-A 发布边界核对 | 查 PR head、main、未决检查、锁定范围、提交差异；根冻结文件不修改 | preflight 记录；相对于 main 的清洁 diff；提交级 CI 状态 | 发现保护区改动时恢复原 blob，不调宽脚本/锁 |
| R24-B 文本必要性审计 | 对 C14 新条款逐段标明确必要/推导必要/条件/可选/未知；检查原需求依据 | 逐项判定和至少一个减负反例；另一读者可重审 | 条款无法解释触发条件则降级/删改 |
| R24-C 静态场景走查 | 用小任务、多输出、独立接收、跨格式等现有 N0–N7；实际手工对照路径，不声称真实 agent 运行 | 静态案例结果、无法检查项与反例 | 不足以支持行为结论，保留待运行 |
| R24-D 公平行为研究 | 宿主能力允许后，冻结**新的未见材料**、同等验收/预算及信息边界；C13/C14 在独立上下文执行 | 实际工具调用、原件/产物、各义务首判；拒绝/失败全部保留 | 无独立环境时 unverified；相互泄漏时实验失去盲性质 |
| R24-E 决策交接 | 对比漏交付、正确率、额外步骤、误拒收、复现和局限；评估是否只吸收小改动 | 升/不升版结论、必要证据、R25 是否值得开始 | 文本更长但无行为改进不得推广为优胜 |
| R24-next | 以前面真实结果选下一问题，写 R25 首项任务、原件、验收并实际执行第一个获授权动作 | 有开始回执才能标 done；否则 blocked/cancelled | 不以仅创建 PLAN 充当启动 |

## R25：从目标自主构造 Agent Flow（P0/P1）

**研究目标**：新上下文没有预写详细方案时，能从真实陌生输入导出必要结果、可执行节点、条件分支、接收接口、职责/工具需求和成本/限制。避免把固定多角色清单当通用架构。

| 工作 | 核心操作 | 交付与验收 | 向前审计 |
| --- | --- | --- | --- |
| R25-01 目标分流器 | 从一段短请求区别直接结果、应用、已有 flow、可复用方法；记录不确定性的后果 | 小任务走直达，复杂任务按风险形成可操作 brief；不制造无用阶段 | 有无未经授权的外部副作用或强制角色 |
| R25-02 结果—接口编译 | 导出必需产物实例与消费者、关键字段/版本/单位；定义依赖顺序 | 能发现隐藏的第二方法/目标，完整追到输出；允许紧凑的模式表达 | 是否漏必要输出、混淆推荐结果与必须交付集合 |
| R25-03 DAG/条件路由 | 节点、触发、依赖、并行域、失败/恢复、stop；与真实 host 接口匹配 | 至少一条端到端可行垂直路径与边界实例 | 是否预设不存在的 Agent/API；是否存在循环/权限扩大 |
| R25-04 未见任务验证 | 选择两个确有不同依赖性质的任务类别，冻结新素材与验收，在新上下文运行 | 原材料→Flow→实际产物/受检切片；针对错项复核 | 对照中“成功设计”与“成功执行”分别判 |
| R25-05 构造器判定 | 与直接路径、C13/C14 适用行为比照任务复杂度和负担 | 可交付构造合同版本；未通过案例/局限 | 不将固定两领域变成所有任务通用配额 |
| R25-next | 实质能力得到适度验证才尝试 R26 执行集成 | R26 首个实际预检回执或明确结束 | 未见成功不得直接宣称自主引擎成熟 |

## R26：真实执行、恢复与交接引擎（P1）

**研究目标**：使设计可在实际允许的宿主中执行，而不把旧 CLI、控制器和工具调用状态重新发明一遍。

| 工作 | 核心操作 | 交付与验收 | 向前审计 |
| --- | --- | --- | --- |
| R26-01 现有能力清点 | 读取真实部署、CLI、provider、浏览器及 lease、host_preflight、pending call 状态 | 能力表区分 available/forbidden/unknown 和实际版本 | 不试探绕过明确宿主拒绝 |
| R26-02 最小执行适配 | 将一个已验收流程映射到实际 host action，返回调用身份与输出 | 真实调度→接收→消费的短路径；不靠模拟替代真实 action | CLI/脚本/原生模型边界清楚 |
| R26-03 恢复与幂等 | 用原件模拟或实施可逆故障：超时、未知创建、部分写、冲突、终止 | 未知副作用先核状态；合法重试不重复写入；原失败保留 | 失败路径有数据丢失/重复提交即拒收 |
| R26-04 独立信息通道 | 组装只含必要原件和验收对象的 packet，观察实际可见历史 | 接收者无预期答案/诊断泄露或标为 unverified | 作者命令/日志/摘要泄漏不可称 blind |
| R26-05 跨环境回归 | 仅测试声称支持的 Windows/WSL/Linux/浏览器/部署环境 | 真实运行与不支持条件报告、包与复现入口 | 文件哈希通过不能代替目标运行时 |
| R26-next | 证明关键链路可运作才启动 R27 学习循环 | 下一研究假设与一次实际反馈处理 | 无后台时仅保存 checkpoint |

## R28：可选的 UI/TUI 调试与能力扩展（条件阶段）

只有 R25–R27 证明流程确实有可观测事件、且用户需要可视化追踪时才启动。可先做纯终端任务图和证据检索，再考虑 GUI；若涉及图形交互需真实浏览器/目标端验收、空/失败/恢复、键盘和响应式。没有实际数据通道和用户价值时，暂缓而非作为所有 Agent Flow 的必经交付。

## 资源、角色与结束规则

- Coordinator/Root 拥有要求、共享状态、最终解释和集成；Worker 负责独立可分配任务；Acceptor 应为真实独立上下文（如果实验要求且宿主支持）。工具不存在时单上下文可实现，但不伪称独立。
- 任务内正常可逆修复按真实信息增益继续；旧受控限额原状保留。重要副作用、费用或权限需对应授权。
- 记录 actual token/cost/model 仅在宿主返回时填值，缺失保持 null。
- 满足用户真实目标、遭遇不可绕过边界、无材料/权限或无新信息可推进时，可以如实结束。阶段末项的“启动下一阶段”并不授予自动无限执行权。
