# Forge 研究入口

本目录保存 Forge 的研发经验、未解决问题和下一步建议，不是让所有 Agent 逐篇阅读的操作手册，也不是已经执行的 R25–R28。**只读与当前决策有关的材料。**

现在的目标是让 Forge 不仅会描述流程，还能根据陌生任务自主设计适合的工作方式、交付可用产物，并从失败中改进。已确认的做法与尚待检验的想法必须分开。

## 现在从哪里开始

如需继续开发，先核对仓库真实状态：`AGENTS.md`、`state/checkpoint.json`、当前分支及未结束的调用。历史 R08 的固定验收仍存在阻塞，R23 定界研究已收尾。正式基线仍是 C13；`C14-hypothesis` 与新建的 `C14-lean` 都属于待实测候选，不能凭文档质量宣布晋级。

接下来优先处理 **R24 的候选比较**：判断精简后的文字是否减少了不必要的操作，同时守住多项交付、真实验收和独立审查。任何前瞻实验都要在看到结果前确定原要求和拒绝条件。缺少合适的新上下文或运行环境时，就把结论限于静态文本评估。

当前已经有一份可直接运行的[交付评测器](../evaluation/README.md)，用于生成简短任务和必须分别交付两种结果的任务，并客观检查输出。它不是 Agent runner；新上下文对照尚待安排。

## 维护时遵守的约定

**让 Skill 负责方法，让研究资料负责证据。** 能用现有段落说明的内容，不另造通用规则；具体失败先放进研究库，等新案例证明它值得推广再写进 Skill。轻任务无需报告矩阵；复杂任务需要结构时，可以选表格、图或 JSON，选择由消费者决定。

文档标题、研究编号和建议阶段是检索入口，不是全部必经的流程。减少重复定义和空泛的“必须”；真正重要的强约束应指出适用条件、错误后果及验证办法。修订时说明改变了什么设计决策、保存原结论，检查链接和实际使用场景。
