# 前瞻审计与防止研发方向漂移

前瞻审计不等同于事后打分：在决定进入下一工作之前，问“下一动作可能无效或制造什么新问题？哪项原证据/反例会让我们停下或转向？”审计结果必须改变真实决策。纯记录型、不能改变决策的清单应精简或删除。

## 三个审计时点

### A. 开始阶段前（Go / Narrow / Block）

核对本阶段与用户目标的必要联系，前阶段是否真正接收、输入原件/冻结版本、已有研究卡是否重复、现实宿主能力和权限、原验收谁判断与什么会失败、是否能在资源允许下完成最小切片。未满足的仅阻塞受影响路径，允许其他独立准备工作。

### B. 有意义的切片之后（Continue / Repair / Branch / Stop）

核查执行产物、消费路径和错误是否真实；本次失败究竟是环境恢复、实质漏洞、评价器错判还是探索负结果；再次尝试新增了什么信息/修改，影响哪些原 gate；是否浪费资源、侵犯原权限或泄露盲审答案。下一步必须有可证伪判断。

### C. 阶段收尾前（Accept / Partial / Reject / Block）

逐项将原要求绑定至原材料、当前产物、实际观察、独立性级别、局限；检查文档与 CI/状态字段同向一致；原始失败和修订是否都保留；下阶段任务是否确实必要、有原件、真实可以开始。只有 actual start evidence 才可标“启动下一阶段任务” done；否则 blocked/cancelled。

## 不变性与交接断言

1. 输入身份、用户原义、原任务的 mandatory 和拒绝条件不能在结果出现后被“解释”为别的任务。
2. 原首次失败和旧固定实验条件不覆盖；知情修订不冒充原始独立成功。
3. 产品 Skill 与研发执行器分开，不能把方法论文字当工具真实可用。
4. 新增通用规则前必须能指出触发条件、反例及避免不必要负担的办法。
5. 文件源、公式/数字、版本、发布时间与最终语言需在消费者处保持可检查的含义。
6. 对任务启动、完成、静态校验、真实 host、独立接收、泛化分别记录证据等级。
7. 下阶段启动必须有合法资源与真实调用，不靠“最后一条 TODO”强制继续。

## 最小审计记录

若当前工作不是单次轻量修改，保存：task_id/phase、时间与实际对象版本、原目标、上一 gate 的证据、风险或未知、所做动作、观察回执、能支持和不能支持的结论、决定 go/narrow/block、责任角色、下一步和停止条件。复杂任务可扩展为表/JSON；普通一步可以一段文字完成。

## 决策优先级

先满足真实原任务和权限，随后保障可复验、避免不可逆副作用，之后才优化效率、体验和可移植性。无实质风险时不增加大规模审批；计划是为了推动验证，不是阻止所有可逆实施。
