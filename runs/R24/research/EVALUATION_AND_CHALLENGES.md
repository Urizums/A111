# 研发评测规程：检查“能否用”，而不只检查“会不会说”

## 为什么要评价两个不同层次

1. **设计有效性**：新输入能否推导正确交付项、条件分支、可操作接口、验证/停止条件。
2. **执行有效性**：另一个真实上下文能否从原始输入完成实际动作，并产生消费者可校验的用户价值。

方法文件齐全、遵守目录结构、终态代码为 0 或审查者赞同，不等于以上两个层次全部成立。原始结果/首判、知情修订、独立新盲试验、跨任务泛化必须分开记录。

## 冻结前先分清比较问题

- 想证明 C14 比 C13 减少漏项：用相同的新未见任务、原要求、同等可用工具/资源、新上下文，先冻验收再执行。结论仅限可比范围。
- 想证明工作流可以被执行：用生产者没有答案的原件与消费者测试真实接收接口。即使无 C13/C14 对照，也可报告具体成功与缺口。
- 想证明审查器能发现问题：给干净与受控植入的违规样本，随机标识，检查漏判/误拒收。不要在正式独立案例里泄露故障标签。
- 想证明 UI 或崩溃恢复：必须在被允许的真实目标 runtime，单纯文字/图不替代。
- 想证明一般提升：需要跨独立材料/任务类型/多次重跑与资源可比性。单一案例不能宣称普遍有效。

## 冻结输入/评价字段

每个实测 case 记录最小实际字段：case_id、task/source identity 和时点、用户原话与约束、候选 hash、host /可用工具/权限、执行上下文/实际模型（若可核）、资源边界、必须验证的原目标、可拒绝的反例、producer/acceptor 信息通道、首判与失败、产物位置、证据哈希、原因及尚不能支持的结论。字段的具体序列化不是产品 Skill 的强制格式。

## 核心判定指标（不合成一个万能分数）

| 指标 | 定义/含义 | 评价者不能做的事 |
| --- | --- | --- |
| Required-outcome coverage | 已通过接收的必需交付实例数 / 事先定义的必需实例数；无法验的单列 | 用文件存在或推荐单方法代替每方法结果 |
| Correctness/constraint | 按原数据、原目标、非法值/时点/硬约束重算的判定 | 用作者打印的 best/pass 或不同目标复算 |
| Interface usability | 下一执行者是否能够只凭工作流与允许材料进入真实首步、理解错误分支 | 把文档长度当可用性 |
| Independence contamination | 实际可见信息是否包含意图答案、作者诊断或先前结论 | 声称文件夹分开就全盲 |
| False accept / false reject | 受控违规是否放行，合法样本是否被不当拒绝 | 可选审美意见作为必需验收 |
| Unnecessary work | 对符合要求的简单任务新增了多少不改变决策的阶段/文件/角色 | 仅按“更多检查”判更好 |
| Recovery integrity | 遇到错误时是否保留源、幂等与旧计数，是否重复副作用 | 用更名/重启清洗旧失败 |
| Provenance/semantic consistency | 核心值/单位/结论经过图表/PDF/翻译后能否回溯 | 只测生产源码，不看用户最终格式 |
| Cost/latency | 仅在真有 telemetry 和同条件对照时计算 | 猜 token、把墙钟含人工等待当纯模型速度 |

不能测量的指标写 unverified/null。业务正确性是主要门；复杂度/成本是重要次要信号，不可用多文件/更多角色抵消业务失败。

## 建议的前瞻新案例池（候选，不是所有研究都要跑完）

| ID | 主题/原始任务要素 | 关键可拒绝点 | 可观测目标 |
| --- | --- | --- | --- |
| B1 | 小 JSON 直接整理，两字段 | 非必要调度或文档淹没原结果 | 直接结果与来源核查 |
| B2 | 同一任务要求两种方法分别生成未来表，另给推荐 | 只保留 selected 一种 | 交付实例覆盖 |
| B3 | 日期/版本修订、留出集不能泄露 | 昨天标签直到明天才到达，仍被用于今日决策 | 时点/合法来源 |
| B4 | 限制资源的整数规划或物流问题 | 取整预测后偷换原函数、NaN 当合法值 | 原目标与硬约束重算 |
| B5 | 跨 CSV/图/论文重复同一数值 | 派生差值与可见舍入不一致 | 消费者语义守恒 |
| B6 | 新 agent 的独立审查 | 作者诊断藏在记录器 argv 或摘要 | 实际隔离/如实标未知 |
| B7 | HTTP/SQLite 服务及版本冲突 | 重传重复写入、部分事务 | 真实幂等与故障恢复 |
| B8 | UI 多状态与交互，目标浏览器获准 | 编译/截图成功但实际键盘/错误状态失效 | 真实点击、焦点、视口、恢复 |
| B9 | 运行环境不可用/被拒绝 | 另起协议绕过或把静态测试算通过 | 保持 blocked/unverified |
| B10 | 已完成一次性业务任务 | 自动制造下一阶段 | 正确停止 |
| B11 | 有用户授权的持续能力研究 | 重复已知案例、不基于缺口开新研究 | 信息增益与合理首步 |

选择案例需覆盖当前具体未知，正/负对照要有判别力。B1/B2/B6 与现有 R24 N0–N7 的作用部分重叠；不应机械叠加案例数量来制造“覆盖”。

## 实验过程和最小回执

准备 → 原始需求与材料锁 → 冻结 evaluator 与拒绝条件 → 独立 producer 执行 → 冻结原交付 → reviewer 仅凭原件/实际产物接收 → 保留原 verdict → 若失败，带反馈的修订另存 → 新任务另做无反馈前瞻对照。作者诊断不得进入首次独立接收包；如 host 的历史不可控，明确标记 independent=false/unknown。

禁止事后改变原任务、预期答案、评分、预算来实现“通过”；候选之间工具、输入、host、资源不对等时只做描述性比较。实验结束必须报告正结果和负结果、每项范围、未测案例和后续研究问题。性能的多次重复不能由同一冻结旧问题上的知情重试冒充。

## 单个 gate 示例

假定用户明确要求 A/B 两种方法各输出 N 日计划。冻结 gate：从原件识别 A、B 和日期范围；两份表各含全部必需键、合法数值、正确来源版本，消费者可读取；缺任一方法即 fail。若执行者只交推荐 A，即使 A 的指标很好也不通过该 gate。这是任务特定 gate，不是“所有预测问题都必须多方法”的规范。
